# MAX 26.31.0 RS V10 — Технический аудит мода

**Версия стока**: 26.31.0 RS
**Версия мода**: V10 (Privacy Mod by JohNick)
**Дата**: 2026-09-20
**Совместимость**: `ru.oneme.app` (Android 8.0–16.0 / API 26–36) · arm64-v8a + armeabi-v7a · основной + клон (`ru.oneme.ap2`)

> **V10**: точечный хотфикс поверх V9 (v26.31.0.9). Устранён баг 2631-F21 — второй, независимый от RuStore self-update путь через HMS AppGallery UpdateSDK, показывавший системный диалог «Обновите приложение / Получите доступ к новым функциям» в обход уже нейтрализованного в V7 RuStore-пути (F20). Дополнительно скрыт пункт «Поделиться логами» из настроек мода (2631-F22) — известная гонка с ленивой Dagger-инициализацией стокового провайдера логов, решение — временно убрать пункт, а не оставлять частично ненадёжным. Fan-out аудит остальных `apply_v_*.py` в этом релизе НЕ проводился (точечный хотфикс, явное решение автора) — область изменений ограничена двумя файлами. Предыдущий публичный релиз — 26.31.0 RS V9 (2026-09-20).

## 🆕 Исправления V10

### 🚫 Self-update через HMS UpdateSDK (2631-F21) — FIXED

**Проблема (репорт пользователя)**: у части пользователей появлялся системный диалог «Обновите приложение / Получите доступ к новым функциям» с кнопками «Обновить и перезапустить»/«В другой раз» — визуально и по формулировке отличный от уже пофикшенного в V7 диалога RuStore (2631-F20). Пользователь явно подтвердил: «это окно стока не мода».

**Причина**: обнаружен второй, независимый self-update путь — `c3/kw.smali` (`extends Lhw;`, тот же абстрактный self-update интерфейс, что и уже пропатченный `c1/vt2.smali`/F20). Метод `a(Landroid/app/Activity;)V`, если RuStore недоступен (`Lcmh;->f()Z`==false), вызывает `Lcom/huawei/hms/jos/JosApps;->getAppUpdateClient(Activity)` → `AppUpdateClient.checkAppUpdate(Context, CheckUpdateCallBack)` — прямой вызов полного HMS AppGallery UpdateSDK (пакет `com.huawei.updatesdk.*`, включая `service/otaupdate/AppUpdateActivity` — именно этот экран и рисует диалог). F20 не покрывал этот путь: `kw.a()` вызывается НЕ через `vt2.a()`/`vt2.c()` (которые уже no-op'нуты), а напрямую из `c3/bv1.smali` (switch-обработчик клика, ветка `:cond_1f2`), которая читает поле `Lvt2;->d:Lkw;` в обход пропатченных методов.

**Фикс**: `apply_v_kill_hms_selfupdate.py` — `kw.a(Landroid/app/Activity;)V` получает `return-void` первой инструкцией, до обращения к полям и вызову HMS SDK. `.registers`/override-контракт с `Lhw;` не тронуты, старый код становится dead-code. `kw.b(...)` не патчился — уже недостижим как dead-code после F20 (вызывался только из недостижимой части `vt2.c()`).

Sentinel: `2631-F21-kill-hms-selfupdate-v1`.

**Верификация**: не воспроизводится на тестовых устройствах (нет HMS Core на S25/HA218XJZ/Redmi) — уверенность в фиксе основана на статическом анализе полной трассировки call-цепочки (`bv1`→`kw.a()`→HMS SDK), а не на device-репродукции самого диалога.

### 🙈 Скрыт пункт «Поделиться логами» (2631-F22)

**Проблема (репорт пользователя)**: кнопка «Поделиться логами» в настройках мода (введена в V6, 2631-A6) иногда выдавала toast «Не удалось запустить сбор логов. Откройте любой экран настроек MAX и повторите».

**Причина**: кнопка вызывает стоковый `Lmrg;->b(Lae5;)V`, но `Lmrg` создаётся Dagger'ом лениво (generic factory-switch `c1/o03.smali::a::pswitch_26`) — только когда граф зависимостей впервые его затребует. Если пользователь не попадал на экран, резолвящий эту DI-ветку, перехваченное поле `AppFlags.stockShareLogsProvider` оставалось `null`.

**Решение**: вместо доп-фикса (расширения точек ленивого захвата — испробовано, не убирает race полностью) — пункт временно скрыт из меню мода по решению пользователя. Реализация: шаг `apply_v_share_logs_button.py` исключён из `make_v1.py::APPLY_STEPS`, изменения кнопки в `smali_inject_v22/c1/one/me/util/AppFlagsView.smali`/`AppFlags.smali` полностью откачены (важно: одного лишь исключения шага недостаточно — mirror-копирование `smali_inject_v22`→`work/baksmali` переносит уже нанесённые правки независимо от APPLY_STEPS). Класс `ModsShareLogs` остаётся скомпилирован как мёртвый недостижимый код (мирроится безусловно отдельно от кнопки) — не влияет на UI.

## ✅ Верификация

- **Сборка**: `make_v1.py --strict --e2e` — все 4 APK прошли gate (`exact_abi`, `no_tracer`, v2+v3 подпись `apksigner`, distinct arm64/armeabi-v7a SHA256). 241 шаг, 0 CRITICAL по статическим гейтам (`reg_collision_gate`, `type_ref_gate`, `undefined_method_gate`, `table_registration_gate`). Только штатные WARN (mipmap ic_launcher default-конфигурация, dex method-refs 94-98% — не относится к патчам).
- **Статическая проверка версии**: единственная строка версии `26.31.0.10` в `classes.dex` (см. HARD-урок `feedback_version_tag_bump_every_release.md` — обязательная постпроверка после инцидента V8).
- **Статическая проверка F22**: `grep -c shareLogs` в `classes.dex` = 1 (только имя мёртвого класса `ModsShareLogs`, не тег кнопки/лейбл — кликабельного виджета в `AppFlagsView` нет).
- **Device-verify Redmi (WGJBBEY9SSMN8TIB)**: main+clone установлены поверх V9 (`adb install -r`), запущены (`monkey -c android.intent.category.LAUNCHER`) — без FATAL EXCEPTION/AndroidRuntime-краша/VerifyError/ANR в logcat, оба процесса (`ru.oneme.app`, `ru.oneme.ap2`) живы после запуска.
- **Не покрыто device-тестом**: непосредственное подавление диалога HMS UpdateSDK — на тестовых устройствах нет HMS Core, баг никогда не воспроизводился локально; визуальное отсутствие пункта «Поделиться логами» в UI также не подтверждено скриншотом (только статически по dex).
- **Fan-out аудит остальных `apply_v_*.py`**: не проводился в этом релизе (явное решение — точечный хотфикс, область изменений ограничена `kw.smali` + `AppFlagsView.smali`/`AppFlags.smali`, не пересекается с остальным пайплайном).
